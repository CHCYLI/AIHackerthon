# Phase 5 executable offline research workflow

Historical Phase 5 checkpoint: the offline CLI and fixtures below remain unchanged.
The separately authorized Phase 6 control plane now supports a guarded live adapter;
see [LIVE_INTEGRATION.md](LIVE_INTEGRATION.md) for its current limits. This page's
original statements about missing live wiring describe the Phase 5 checkpoint,
not proof of current live research or authorization.

**TEST DATA — simulated demonstration, not real research findings.** No network,
wallet, hosted LLM backend, API key, real recipient or live Flashpoint adapter is
used. Existing Carbon Twin calculations and Phase 3 guards are reused unchanged.

## Reproduce

From the repository root, using the existing Node 22.23.5 runtime:

```powershell
& '..\release-assets\node.exe' scripts/challenge-run.cjs demo
& '..\release-assets\node.exe' scripts/challenge-run.cjs demo --case empty
& '..\release-assets\node.exe' scripts/challenge-run.cjs demo --case pending
```

Each command without `--dir` creates a different ignored directory under
`.runtime/challenge/phase5/`. Supply `--dir .runtime/challenge/phase5/my-demo`
for a named directory. A completed rerun returns the saved report without new
actions/events; an incomplete directory is preserved and requires explicit
inspection/resume. Do not remove an incomplete run to bypass uncertainty.
With a supported Node on PATH, `npm run challenge:offline` runs the valid demo;
`npm run challenge:offline -- --case empty` runs the empty-answer case.

The valid demo replays this Phase 5 session's **recorded Codex judgments** from
`fixtures/codex-decisions/`. It does not ask an automated LLM to reason anew.
Every replay must match its semantic `basisHash`: objective, actual model context,
authored plans, prior analysis and validated answer values/counts. Changing those
inputs rejects the recording (`REPLAY_INPUT_MISMATCH`) and requires a fresh Codex
decision. Run-specific artifact/evidence references are resolved against that
run's own validated questions, never copied from the authoring run.

The valid demonstration has two optional-policy rounds selected by the recorded
Codex decision, not by a rule in the simulator. Round 1: COMPLETE 6, retrieved 8,
usable 4, denominators 4/4/4/4/3. Duplicate copies (2), a malformed row (1) and a
preview (1) are excluded. Round 2: COMPLETE/retrieved/usable 3/3/3, both question
denominators 3. The recommendation demonstrates an NPV sign/time/units explanation,
with carbon-definition and no-change counterevidence. It proves no real UI effect.

`empty` returns `INSUFFICIENT_EVIDENCE`, COMPLETE/retrieved/usable 12/12/0 and
`BLOCKED`, with no analysis, follow-up or final report. `pending` leaves the first
draft request unapproved and makes zero simulator business calls.

Additional cases: `create-fail`, `unknown`, `delayed`, `retrieval-fail`, `invalid`,
`payment-required`. A delayed answer needs a separate explicit read; no polling,
invitation, payment or unknown operation is automatically retried. The simulated
402 creates no payment signature. Unknown outcomes retain receipts and block replay.

## Codex-driven steps for new judgments

The workflow never produces survey questions, interpretations or recommendations
from deterministic rules. Codex reads `agent.md` and an actual checkpoint, then
supplies a JSON decision. For example:

```powershell
& '..\release-assets\node.exe' scripts/challenge-run.cjs init --dir .runtime/challenge/phase5/manual --objective 'The research objective'
& '..\release-assets\node.exe' scripts/challenge-run.cjs checkpoint --dir .runtime/challenge/phase5/manual --kind PLAN
& '..\release-assets\node.exe' scripts/challenge-run.cjs submit --dir .runtime/challenge/phase5/manual --file .runtime/challenge/phase5/manual/codex-output.json
```

Codex writes `codex-output.json` after inspecting the checkpoint; that file is an
input, not generated by the three commands above. For arbitrary new questions,
provide correspondingly scoped TEST DATA through the adapter's `fixture` option;
the bundled fixture rejects unknown question IDs instead of fabricating answers.

Decision envelope: `{schemaVersion: 1, label: 'TEST DATA', origin: 'CODEX_AUTHORED',
kind, inputHash, basisHash, payload}`. Copy both hashes from the current checkpoint.
`inputHash` binds the exact run/stage/references; `basisHash` binds semantic inputs.
Examples in `fixtures/codex-decisions/` are actual outputs recorded during this
session, including their original input hashes. Neither an origin string nor
local validation cryptographically attests LLM authorship or scientific truth.

| Kind and current stage | Required payload and deterministic validation |
| --- | --- |
| `PLAN` at `DRAFT_PLAN` | `interpretation`, `participants`, `analysisCriteria`, declared `uncertainties[{id,rationale}]`, unique `questions[{id,type,prompt,rationale,uncertaintyIds,options?}]`; no assumed provider IDs or prior findings. |
| `ANALYSIS` at `ANSWERS_VALIDATED` | `findings[{claim,support}]`, `counterevidence`, `unresolved[{question,support}]`, `limitations`; positive-denominator scoped question evidence required. Codex judges meaning. |
| `FOLLOWUP` at `ROUND_1_ANALYZED` | `decision: STOP or CREATE_FOLLOWUP`, concise `reasoningSummary`, `support`, and `plan` only if continuing. Every follow-up question needs its own Round 1 `support`. No generic Round 2 is generated. |
| `FINAL` after Round 1 `STOP` or at `ROUND_2_ANALYZED` | One `recommendation`, `support`, `counterevidence`, `limitations`, `nextCheck`; report persists before `COMPLETED`. |

`support` is an array of `{round, questionId}` using planning IDs. The workflow
resolves these to exact validated `evidence:...:providerQuestionId` references and
logs them. Missing evidence fails closed. The checkpoint includes private
normalized records for Codex interpretation; state and event logs omit answers.
Keep checkpoint files private. No raw answer or contact data belongs in summaries.

## Execution, approval and adapter boundary

`createWorkflow({directory, adapter})` exports `initialize`, `state`,
`prepareContext`, `checkpoint`, `submit`, `requestAction`, `approve`, `execute`,
`retrieve`, `recover`, `reconcile`, `resume`, `report` and `readArtifact`, plus the
existing `store`. Await `execute()`, `retrieve()` and `reconcile()`; adapter methods
may be synchronous or asynchronous. Other workflow methods are local/synchronous.
Live adapters are refused in Phase 5. The mode flag is a local contract, not a
sandbox for arbitrary untrusted JavaScript.

CLI actions use `request --kind create_survey|publish|email_send`, then
`approve --approval ID --hash HASH` (or `reject`), then `execute`, always with the
same `--dir`. Approval commands explicitly simulate a decision for TEST DATA only.
They authorize no live action. Manifest hashes bind the full reviewed scope, plan,
tool input, run/round, recipient fingerprint/count, zero ceiling and zero retries.
They use `challenge-safety.digest`; they are not the wallet wrapper's narrower
`requestHash`. A future approved transport must preserve both applicable guards.

The module supports `requestAction(kind, {maxChargeUsd, recipientIds})`; a positive
ceiling is rejected by the existing null-budget guard. Only unique `TEST-recipient-*`
IDs are accepted for simulated email, with a labeled mock consent artifact and
fingerprint. No addresses, SMTP or remote recipient upload exist. The real recipient
delivery mechanism remains a Phase 6 dependency, not an implemented MCP parameter.

Boundary operations use `tool_survey` with only `brief`, `survey_id` and
`conversation_id`, following the saved Phase 2 input schema and description.
Draft creation omits IDs; subsequent requests thread the returned IDs. Status input
is `panel` with `action: 'status'`, required known `job_id`, optional conversation ID.
The latter yields only mocked progress, not answer evidence. Publication,
distribution and readback are natural-language survey requests; there are no
invented MCP publish/email/retrieve tools or structured parameters.

`flashpoint-tool-contract.json` is copied from authenticated Phase 2 discovery,
dated `2026-11-22T04:41:49.179Z`, Flashpoint.AI 1.30.0. It proves input shape and
advertised capabilities only. Refresh before live work. No authentic output schema
is verified. Simulator envelopes (`mock: true`, `label: TEST DATA`,
`adapter: offline-flashpoint-v1`) are **local test contracts**, not platform API
responses. `normalizeAnswers()` rejects unknown/live envelopes and maps only the
mock envelope to the unchanged Phase 3 schema; the existing validator then checks
source, scope, IDs, mappings, rows, exclusions and denominators.

The simulator's survey/conversation/panel/provider-run IDs are opaque `TEST-*`
identifiers stable for fixture replay. Internal research run IDs remain unique.
They are stored exactly as returned, never treated as real platform IDs. The
draft receipt carries an explicit planning-to-provider question-ID map.

## Persistence and recovery

Each run stores existing `run-state.json` / `events.jsonl`, content-addressed
private `artifacts/`, a durable `offline-adapter.json` receipt ledger and `report.md`
when complete. `file:artifacts/HASH.json` references are relative to that run;
hash verification detects artifact changes. The report links a structured report
artifact and the exact question references. Model context uses actual calculations.
Mock approvals, platform actions and findings remain separately labeled.

`recover` marks in-flight intents unknown using Phase 3 recovery. Inspect `show`,
then explicitly `reconcile --action ACTION_ID` against the simulator's durable
receipt, then `resume`. Only confirmed `SUCCEEDED` or `NOT_EXECUTED` reconciles;
unknown remains blocked, with no automatic retry. A verified non-execution still
needs a fresh request approval. Simulator creation failure and unsigned 402 are
recorded as non-executed; neither implies reusable approval.

`resume` can finish saved local stage acknowledgements and restore persisted
Codex decisions without dispatching tools. It never clears live locks or corrupt
journals. Interrupted simulator locks/files require explicit inspection; no
distributed exactly-once or cross-file transaction is claimed. `retrieve()` reuses
already saved evidence for local recovery. After a resolved blocker, explicit
`await workflow.retrieve({refresh: true})` requests a fresh read; this is never a
background retry and currently works only with the offline adapter.
